# Debugger API review

Static review of `tools/research/hw_watch.py` and `debug_assert.py`, 2026-11-05. No debugger attached; no target changes. Graphify located `Context`, `watch()`, `observe()` and related helpers; findings below checked against current source and Microsoft documentation.

## Confirmed implementation defects

- **Exited threads remain in watcher map.** `hw_watch.py:117-121` retains event-provided thread handles, but event dispatch has no `EXIT_THREAD_DEBUG_EVENT` branch. Windows closes that event handle when exit event is continued. Cleanup at lines 150-153 therefore attempts suspension/context access/close using stale values for threads that exited during observation. Process exit also automatically closes corresponding event handles, yet final close loop still runs. Remove exited entries; use explicit ownership for any independently opened/duplicated handles. [WaitForDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent)

- **Existing debug state is overwritten, never restored.** `arm()` replaces DR0-DR3, DR6 and DR7 (`hw_watch.py:65-73`). `disarm()` calls same function with empty addresses and zero control (`76-82`); original values are never saved. This changes thread register state even though process memory is not written. Context flags also request control and integer state when only debug state needs modification. Windows sets portions selected by `ContextFlags`, with OS-controlled fields potentially sanitized. Preserve original debug configuration or reject conflicting pre-existing configuration; restrict write scope. [SetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setthreadcontext)

- **Exception ownership is not checked.** `hw_watch.py:128-141` consumes every `EXCEPTION_SINGLE_STEP` from a tracked thread, including failed context reads and `slot == -1`. It counts only first set slot, without confirming slot belongs to successfully armed watcher state. Single-step exception can represent trace execution, not merely this watcher's data breakpoint. Pass through unowned events; classify owned hits before handling or clearing status. [GetExceptionCode](https://learn.microsoft.com/en-us/windows/win32/debug/getexceptioncode)

- **Every breakpoint exception is swallowed.** `hw_watch.py:111,142-144` leaves `DBG_CONTINUE` for all breakpoint exceptions, including later target-generated ones. Windows treats that status as handled and stops exception dispatch. Track expected attach breakpoint and pass through subsequent unowned exceptions. `debug_assert.py:363-367` already narrows handling to first first-chance breakpoint; that is a useful improvement, although code alone does not prove every possible first breakpoint is attach-generated. [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent), [DebugActiveProcess](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocess)

- **API errors lose diagnostic evidence.** `hw_watch.py:106,109-110,141,144,151,155` ignores kill-on-exit policy failure, treats every wait failure as timeout, ignores context-clear and continuation failures, and ignores disarm/detach failure except aggregate disarm count. Consequently, zero hits cannot distinguish no accesses from failed instrumentation. APIs expose failure and extended error information; capture operation, thread ID and error immediately. `debug_assert.py` checks wait/continue and initial kill-on-exit policy, but final detach return at line 385 is still ignored. [WaitForDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent), [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent), [DebugActiveProcessStop](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocessstop)

- **Preserve-target policy is unchecked.** `hw_watch.py:106` ignores `DebugSetProcessKillOnExit(False)` result. Default policy terminates attached processes when debugger thread exits; successful `False` changes this to detach. Unchecked failure undermines cleanup guarantee, particularly if detach also fails. [DebugSetProcessKillOnExit](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-debugsetprocesskillonexit)

- **Cleanup is not a verified stopped-state transaction.** Normal loop continues last event before timeout/hit cap, then `finally` suspends, clears and resumes one thread at a time (`hw_watch.py:144-155`). Other threads can run or trigger events during cleanup; event loop is no longer servicing those events. Individual `disarm()` does suspend before context access, which is correct locally, but whole-process restoration and balanced resume are not verified. An exception in event processing also bypasses `ContinueDebugEvent` because watcher lacks per-event `finally`; `debug_assert.py:377-380` has that protection. Coordinate restoration while debugging event holds process stopped, account for live-thread ownership, check restoration/resume/detach results. Actual runtime outcome remains untested. [Debugger main loop](https://learn.microsoft.com/en-us/windows/win32/debug/writing-the-debugger-s-main-loop), [GetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext), [SetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setthreadcontext)

## Explanations not established

Event thread handles are **not documented as lacking context-write rights**: valid `CREATE_THREAD_DEBUG_INFO.hThread` and initial `CREATE_PROCESS_DEBUG_INFO.hThread` grant `THREAD_GET_CONTEXT`, `THREAD_SET_CONTEXT` and `THREAD_SUSPEND_RESUME`. Independently opened handles would need those requested rights; observer's `OpenThread(THREAD_GET_CONTEXT)` is appropriate for its read-only context use. [CREATE_THREAD_DEBUG_INFO](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-create_thread_debug_info), [CREATE_PROCESS_DEBUG_INFO](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-create_process_debug_info)

Context access during an outstanding debugging event is **not evidence of unsuspended-thread misuse**: Windows suspends process threads when delivering event, and permits debugger context inspection/modification before continuation. Both tools perform event-time reads there. [Debugger main loop](https://learn.microsoft.com/en-us/windows/win32/debug/writing-the-debugger-s-main-loop)

Zero hits, failed attachment or target exit **does not prove anti-debug detection**. Watcher defects above, failed APIs, inactive watched data and ordinary target exceptions remain competing explanations. First-chance exception is also not proof of fatal failure: passing it unhandled permits target exception handlers; second-chance unhandled continuation terminates process. [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent)

Limits: no live reproduction, anti-debug path analysis, CPU-manual DR6/DR7 audit, or fix implementation. Findings prove code paths and API contracts, not cause of any particular observed game exit. No claim that hardware watchpoints are intrinsically unusable on this client.
