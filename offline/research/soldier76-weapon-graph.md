# Soldier: 76 weapon graph support in build 1.74

Scope: source/data review pinned to Boi-027 `overwatch-1.74-lobby-server` commit `0fa61b950dfc9c915cb2353d2873d6d4689c2a5e`, plus bounded retail 1.74 runtime observations recorded below.

Current runtime status supersedes the earlier experiment notes: held-rifle rendering works in the normal launcher; native jump/landing and one spawn-wall collision are verified. HUD, firing, damage and bots remain incomplete. Body command acknowledgements are implemented. Latest state-payload/event-boundary findings and evidence are in [the runtime report](soldier-runtime/REPORT.md).

## Findings

- `game_heroes_174.json` maps Soldier: 76 (`0x02E000000000006E`) to body definition `0x04000000000003CF`. The extracted hero record lists Heavy Pulse Rifle as the hero's sole `Weapon` loadout. `game_graphs_174.json.gz` maps that body to weapon graph `596` in its `weapons` array (`[null, 596, null]`). This ties graph 596 to Soldier's weapon component; calling it the Heavy Pulse Rifle graph is a strong catalog-based inference, not a graph name present in the dump.
- Graph 596 has 155 nodes, 85 state entries, 81 networked owner states, and 128 sync-variable slots, of which 51 have identifiers. Its weapon-volley state nodes are at graph state-list indices `10` and `16` (node positions `25` and `38`). Both node classes and their serialized fields are present in the pinned graph dump.
- The graph contains logical-button IDs `14`, `20`, and `29`; the ID-20 node connects through nodes `33 → 63 → 101 → 117` to volley node `25` (state index 10). ID 29 connects through `46 → 37 → 64` to volley node `38` (state index 16). This is an exact graph-link traversal. The dump does not name those logical-button enum values, so ID 20 is only a candidate for the primary-fire path; do not equate it with the packet FIRE bit without a verified enum mapping.
- Volley node 25 references dynamic variable `842` and entity definitions `0x0400000000001C85` and `0x04000000000003D4`. Volley node 38 references `0x0400000000001C86` and `0x040000000000072C`, and includes projectile speed `50` and lifetime `5`. These records confirm weapon graph logic reaches projectile-volley states; the extracted node fields alone do not establish hit registration or damage semantics.
- The current repo has no firing implementation. `WIP.md` explicitly lists weapons, abilities, and HUD as unfinished: client prediction rolls them back without server replies, so the server must run hero statescript graphs. The graph module is a static metadata loader; `statescript.py` is a frame encoder, not an interpreter. Its protocol notes say client runs graphs, server supplies graph instances/states/variables, server-created instances do not run Entry nodes, and the server must send the state/variable results those entries would produce.
- Soldier body `0x04000000000003CF` declares manager graph `21` (`0x15`), body graphs `[51, 75, 67, 593, 597, 599, 601, 2331, 2230]`, and weapon scripts `[null, 596, null]`; slot 1 therefore references graph 596. Manager graph `0x15` contains logical-button nodes for IDs `17`, `16`, `15`, `22`, and `21`, but the dump provides no readable mapping from those numeric IDs to movement actions. Its Entry node 0 targets node 72; that node computes variables `9526` and `9573`, whose names/meaning are not present in the dump. No graph-`0x15` node references graph 596, so no separate manager state that starts the weapon was identified.
- Graph 596's root Entry node 0 links to node 123 (state 64, owner-frame bit 60) and node 127 (`ActionSetVar`, variable 476 set to float `20`). That is the graph's own Entry output, not a parent-manager trigger. Because server-created graph instances do not run Entry nodes, a working weapon instance needs these results plus subsequent graph states/variables; activating a single volley state is insufficient evidence of a firing implementation. The local server currently creates the body/movement record and the player's controller script, but no body or weapon graph instance (`tools/lobby/vendor/ow174/game/match.py`, `spawn_updates`, `own_body_updates`, and `send_controller`).

## Runtime observations

- Retail 1.74 reached the Practice Range first-person view through two menu-entry/hero-selection/teardown cycles. Input diagnostics read forward `127`, Space `40`, and FIRE bit `1`. About 150 W key pulses visibly moved the viewpoint toward a door; walking was confirmed. Jump flight was not verified.
- Soldier's rifle and in-game HUD remained absent, and firing produced no visible shot. The HUD-only experiment activated owner bit 0 on graph `0x20E4`; it caused no visible change. The client exited through the normal menu with code `0`, and both loopback ports were released.
- Graph `0x20E4` has one owner state: node 34, state 25, class `STU_9D7BF987`. It is also the only remote-state entry. Special Entry node 33 links directly to node 34's begin plug; the node has no child subgraph or begin/end output links. Owner bit 0 therefore maps to the graph's only owner state, but the runtime test shows that activating this bit alone does not make the HUD visible.
- Scope correction: `graph.py` defines `INSTANCE = 0` and `ENTITY = 1`; presence bits exist only for non-null sync variables with instance scope. Graph `0x20E4` has two non-null entries, IDs `18405` and `17906`, both entity-scoped, so its instance-presence count is zero and `HUD = Graph(0x20E4, 1, 0)` is consistent. Node 34 references those two entity variables and remote-sync IDs `0x0D800000000045F2` and `0x0D800000000047E5`; they are not omitted per-instance presence payloads. The negative bit-0 test does not establish whether the HUD needs entity-variable values or further graph states.

## What can be reused

- Reuse `ow174/game/script/graph.py` and `data/game_graphs_174.json.gz` for build-specific body-to-weapon graph lookup, node classes/links, state indices, and schema data. The data's provenance is documented in the module header: generated from DataTool's XML dump.
- Reuse `ow174/game/commands.py` to decode client command frames; its `FIRE` and `SECONDARY` packet bits are `0x01` and `0x02`. No source reviewed here maps those packet bits to graph logical-button IDs 14/20/29.
- Reuse `ow174/game/statescript.py` to encode full owner frames and graph state/variable payloads. `Instance.active`, `presence`, and `extra` allow explicit state and variable values, but caller must compute them. Existing frame tests validate serialization only; they do not test firing.

## Minimum implementation judgment

A full interpreter for every Overwatch graph is not required to explore a Soldier-only firing slice. A narrowly scoped interpreter for graph 596 could be attempted, but it still needs correct body/weapon graph initialization, Entry-node results, FIRE-command to logical-button mapping, the boolean-switch/stack/action state transitions, per-frame ammo/cooldown and sync variables, and authoritative owner-state replies that prevent client prediction rollback. A single hard-coded volley-state bit is not supported by this evidence as sufficient for a persistent shot or hit. The repo's own WIP calls for running the hero statescript graphs; a narrower substitute is an unverified implementation choice that must be tested in-game later.

## Weapon draw path review

The selected weapon's strongest model/attachment candidate is graph 596 node 31 (`STUStatescriptStateCosmeticEntity`, state-list index 11), reached when root node 1's selected-weapon BooleanSwitch takes its true subgraph and child node 32 evaluates false. Node 1 compares dynamic var 31 (entity scope) with var 28 (instance scope); node 32 tests entity-scope var 34 and its false subgraph links to node 31. Node 31 names entity definition `0x04000000000004BF`, writes dynamic var 49, and carries identifier `0x0D80000000000F5E`. It attaches at hardpoint `0x0DC000000000000A`; its arm IK records reference hardpoint `0x0DC000000000000B`, bones `0x088000000000001C` and `0x088000000000002E`, and weight dataflow `0x0480000000000069`. These fields make node 31 a strong held-entity/weapon-draw candidate. The checked catalogs do not resolve definition `0x04000000000004BF` to a display name, so its identification as Soldier's rifle remains an inference.

Graph 596's native Entry node 0 links to node 123 (state index 64) and ActionSetVar node 127. Node 123 initializes dynamic var 472 with `STU_7197C080`: integer fields 6 and 0 plus a dynamic var 9744 value with default dynamic var 9528. Node 127 sets dynamic var 476 to float 20, then links to action node 14. The Entry chain does not assign vars 31, 28, 34, or 49. Therefore, the literal Entry outputs alone do not satisfy the selected-weapon gate or prove that the cosmetic entity will be created. The weapon graph also has message-driven entries, but none of their direct Entry outputs initializes these four identifiers; they must be supplied/produced by the associated manager and graph-state execution.

Within the selected branch, nodes 41 and 13 are dataflow mappings (`0x04800000000000F7` → var 1769, and `0x048000000000006C` → var 689), while node 67 is a state stack writing entity var 243 from an expression over vars 229–231. Node 31 is the only node in this branch with both an explicit entity-definition field and dynamic var 49. The volley nodes 25 and 38 also reference var 49, consistent with reuse of that entity handle, but this linkage does not by itself prove node 31's display model or complete weapon initialization.

This narrows the root's state requirements: initialize the manager/weapon selection so node 1's var31/var28 comparison succeeds; produce var34=false for node 32's false branch; then send node31's owner state with its var49 cosmetic-entity data. Exact server encoding of a `STUStatescriptStateCosmeticEntity` state and the dynamic entity instance payload was not established by this review. Do not treat this as a confirmed one-state rifle fix.

The associated manager graph 21 starts at Entry node 0, which links to node 72 (`STU_12F5D52D`). Node 72's multi-set list initializes entity var 31 to integer 0, and entity var 30 from dynamic var 16515, alongside other animation defaults. This is a catalog-backed initial value for the manager's var31; the weapon graph's var28 is instance-scoped and is not initialized by graph 596's Entry chain. For graph596 node 1's true branch, var28 therefore must be populated with the selected manager value (initially 0 if the default selection remains active). The graph data alone does not establish who writes var28 or the meaning/source of var34; node32's false-to-node31 branch is the only observed gate for the cosmetic entity.

The graph596 `sync_vars` table locates var28 at index 29 (instance scope), var31 at 31 (entity scope), var34 at 34 (entity scope), and var49 at 50 (instance scope). Vars472 and 476 are instance-scoped at indices 88 and 92; var243 is entity-scoped. This separates required frame presence from entity values: var28/49/472/476 participate in per-instance presence, while var31/34 do not. Node31 is networked owner state 11 and lists entity-scoped remote sync IDs `0x0D80000000000022` and `0x0D800000000001DE` in both its input/output sync lists.

## First body-frame assertion review

The supplied first-body-frame experiment reported client assertion `F0E7E025` at line 85 with condition `D62712AE` and message `D47CD445`, then exit `0x80000003`. That observation does not identify the bad field by itself.

- The 81 owner bits and 23 presence bits are correct for graph 596. The graph has 85 state entries; filtering the four non-owner entries leaves 81. Its 128 sync-var slots yield 23 non-null instance-scope entries. Node 31 (state-list index 11) is networked, so it maps to owner-state bit 11; it is not a SubScript state. `Instance.active[11] = None` therefore emits its active bit with no child-instance payload. The local serializer has explicit extra payload handling only when callers supply a payload (including the SubScript helper); no pinned golden frame exercises a CosmeticEntity state.
- Presence keys in `Instance.presence` are bit positions among the filtered instance-scope entries. Graph596 order is: bit 0→2316, 1→2447, 2→2575, 3→10268, 4→28, 5→173, 6→689, 7→49, 8→53, 9→699, 10→61, 11→831, 12→581, 13→198, 14→472, 15→476, 16→31196, 17→229, 18→230, 19→231, 20→1769, 21→1770, 22→8183. The current `soldier.py` experiment sets only bits 4, 8, 12, 13, 15, 17, 18, 20 and 21. In particular, it leaves bit 7 / var49 absent although node31 writes var49. Since this is a full frame, the omitted bit is serialized as absent; whether that is invalid before the state executes is unresolved.
- The owner-frame code encodes `Bool` as tag 0 plus one boolean bit and `Int` as tag 4 plus a 32-bit value (`statescript.py:51-70`). Upstream golden tests cover known client frames with booleans and frames with no variables, but contain no `Int`, `Asset`, or `Entity` value fixture (`tests/test_game_statescript.py`). Thus the `Int` tag is implemented in source but not independently validated against a native client. The failing body frame includes several `Int` values, making type encoding a plausible investigation lead, not a confirmed cause. Integer vars31/28 are consistent with graph596's equality condition and manager21's explicit integer initialization of entity var31 to 0.
- The exact body record lists nine initial body graphs `[51, 75, 67, 593, 597, 599, 601, 2331, 2230]`, manager 21, and weapon graph 596. Therefore 81/23 describes the weapon graph instance alone, not a complete count for every graph referenced by Soldier's body. The owner-frame encoder documents that a full frame destroys network instances not listed (`statescript.py:10-16`). If the experiment sent only graph596 instance 1 as the body's full graph list, it omitted the other catalog references. This is a structural discrepancy to check against the runtime frame, not proof that every listed graph must be server-instantiated.
- Node31's variable49 is an instance-scope dynamic output, while node31 also has two entity-scope remote-sync identifiers (`...0022`, `...01DE`). The graph dump does not expose the serialized value type or prove that the client needs var49 preseeded before evaluating state11. The input state bitmap has no proven CosmeticEntity-specific payload beyond its active bit. Both remain open; do not guess an `Entity` or `Int` value for var49 based only on its dynamic-variable declaration.
- Root node1's selected-weapon true subgraph links 14 children: positions `[2, 41, 67, 13, 24, 32, 40, 55, 68, 69, 70, 72, 85, 164]`, whose state-list indices are `[1, 18, 32, 6, 9, 12, 17, 22, 33, 34, 35, 37, 45, 83]`. The current `soldier.py` experiment activates only owner bits `{0, 11, 12, 60}`; it omits all but child state 12. The graph links imply a larger selected branch than this bitmap describes. Whether every linked state must be marked active in the authoritative owner frame is not proven by a graph596 native oracle, but the omission is a concrete candidate for the assertion or missing weapon.

This narrows native triage to independently confirming (1) presence bit order and var49 omission, (2) whether `Int` tag 4 is accepted, and (3) the actual descriptor list and entity/per-instance variable blocks in the body frame. These checks do not alter the earlier inference that node31 is the held-weapon draw candidate.

## Fire animation (open, 2026-11-02)

The first-person rifle does not kick when firing. Tracking a fixed point on the gun (its cyan triangle) through 5.5 fps captures shows only the slow idle sway (about ±3 px over 2 s), the same before, during and after a 2 s burst. The camera's vertical recoil and the muzzle flash/tracers do play.

Ruled out, each tested in game (sessions `20261102T055526`, `055857`, `060134`, `060432`):

1. **Volley 10 held on through the burst** (one Start, a shot-count update per pulse, Stop on release). This matches native automatic fire and is kept, but it brings no kick.
2. **Volley 10's shot outputs ChaseVar st19/st20** (vars 1769/1770 to 100, read by DataFlowMappings st18/st17) with the ChaseVar f32 at 0 and at 100: no kick. Reverted.
3. **Root children Stack st32** (entity var243 from vars 229–231) **and DataFlowMapping st5** (var243 → data-flow 0x37): no kick. Reverted.

Not anim states: st7 and st39 are both reload animations (aliases `0x10B`/`0x004`, chosen by entity var842).

Static trace (`fire-animation-trace.md`, IDA only):
- Per-shot path: Volley DSR `0x7FF6D1F80400` → update `0x7FF6D1D05D90` → scheduler `0x7FF6D1F81070` → executor `0x7FF6D1D06DF0` (dedup `0x7FF6D1D07D50` lets fresh server shots through) → effect spawner `0x7FF6D1D064F0`.
- The spawner ends with the only anim-like call found: `0x7FF6D17EFB90(animObj, [info+0x40], ms)` at `0x7FF6D1D06DA4`. It runs only when the predicate `0x7FF6D17A74F0` holds (a typed component of the script's entity belongs to that entity) and `[info+0x40]` is non-null.
- `info` is a resolved per-weapon struct (`0x7FF6D1F7E030`, table `0x7FF6D1FA6660`, keyed on Volley `+0x1C0`).
- Runtime check (`fire-animation-trace.md`, last section): `[info+0x40]` is the anim-recoil block and every gate passes, but the play call never re-triggers for server-driven shots. Second check: during a held burst the client's Volley 10 never activates at all; it ran only once, as a magazine emptied. Prediction experiments (same file, last section): the descriptor flag bit makes the client predict the rifle, and the Volley DSR's first value is ms since begin. Together they make held-fire Volleys and the kick spring run, but camera recoil then compounds, so both stay off.

Next leads:
- The Volley's `projectileVisual.animRecoilImpulseFactor` (0.1) sits at ProjectileVisual +0x18 (field table near `0x7FF6D43FA7E8`). Find its runtime consumer.
- Find whether the owner applies the impulse only to shots it predicts itself, rather than to server-driven Volley counts.
