# Practice HUD client Entry condition

## Catalog facts

The pinned 1.74 graph catalog row with index `8420` (graph resource `0x20E4`) has client-only Entry node position 8, which links directly to client-only BooleanSwitch node position 10/state 8. The switch true subgraph lists state 5; the false subgraph is empty. Its condition is `STU_919FD47C` with opcode bytes `[14, 0, 7, 0, 15, 0]`, one config-var object of class `STU_A3DEF368`, and one dynamic-var object: identifier `23604`, `m_60DB8F99=0`, `m_EE729DCB=0`. Graph 8420's synchronized-variable table contains only entity vars `18405` and `17906`; it has no entry for `23604`. The sequence and fields are directly inspectable in the pinned [1.74 graph catalog](https://github.com/Boi-027/overwatch-1.74-lobby-server/blob/0fa61b950dfc9c915cb2353d2873d6d4689c2a5e/data/game_graphs_174.json.gz).

The `0` scope discriminator distinguishes this input from the entity-scoped variables (`m_60DB8F99=1`) in the same graph’s sync table. It is therefore a graph-instance/local variable reference, not evidence for a player or body entity. Because the switch is client-only and its variable is not in the graph’s synchronized list, the catalog does not establish a server-set value or a serialized presence bit for it.

The earlier `STU_A3DEF368 +0xC8` callback observation is not the callback used by this condition path; it does not identify this condition’s value or semantics. The graph record still provides no default or value for identifier `23604`.

## Opcode boundary

The local beta `Prometheus-Core` header documents opcode meanings for values such as `0–5`, `30–40`, `70`, and `100+` ([Statescript.h, lines 370–408](<beta-project>/repo/Prometheus-Core/Statescript.h#L370)). Its parser dispatches those implementations and returns no implementation for other values ([StatescriptExpressionParser.h, lines 2717–2838](<beta-project>/repo/Prometheus-Core/StatescriptExpressionParser.h#L2717)). It has no definitions for retail sequence values `14`, `7`, or `15`, so mapping this expression from beta opcode semantics would be unsupported. The local catalog represents `m_opcodes` as the byte sequence above; it does not separate these values into a typed operator/operand structure.

The local catalog still does not name the value type or provide a default for identifier `23604`. The retail VM trace below decodes its lookup path; the later guarded runtime decode identifies the returned entity as GameMode `0xD0000010` in that capture.

## A3 source-entity path

The VM’s actual call arguments rule out the earlier `ScriptInstance +0x10` assumption: BooleanSwitch `+0xB8` passes `[state+0x78]` as evaluator `RDX`; the VM saves that as `r14`; case 14 passes `RDX=r14` through the config-var wrapper. A3 `+0x20` therefore receives the ScriptInstance itself as its context.

In historical PID `29392` capture [live graph metadata](../.scratchpad/live-graphs-29392.json), state-8 ScriptInstance pointer was `0x25F8D841490`, with vtable VA `0x7FF6D384E740`. Its `+0x90` method at VA `0x7FF6D1F45220` calls its own vtable `+0x60` (`0x7FF6D35FC640`) to obtain SyncMgr, then dispatches SyncMgr vtable `+0x240` at VA `0x7FF6D1B99280`. Captured SyncMgr mode `+0x4C0` was `0`; case 0 reaches `sub_7FF6D1F2D9E0`, which tailcalls `sub_7FF6D2A462B0` with `[SyncMgr+0x528]`. These pointers are historical and must not be reused after process exit.

`sub_7FF6D2A462B0` decodes that reference using the **runtime** qword at VA `0x7FF6D41047FC`, ROL 2, and XOR `0xF320E42472A94F14`; it dereferences `+0x28` and XORs `0x98DE97B50B3BE1E3`. The live runtime key was `0x24254C94F1874F43` (the IDB’s on-disk bytes differ). This yielded sourceEntity pointer `0x25F8D5CA140` for this capture.

A3 `+0x20` then calls `sub_7FF6D1F2A0A0` on that sourceEntity and, on its successful path, `sub_7FF6D2A462E0`. A3 serializes the returned pointer through `sub_7FF6D2186C80` as wrapper kind `0x0A`, copying its first 32-bit word. The initial static trace did not identify that word; the guarded live decode below later returned `0xD0000010`. SourceEntity `+0x08 = 0x3B403601` is not the returned network ID.


A bounded follow-up read in that historical capture found `sourceEntity+0xE0 = 0x25F8FF27608`. At index 114 (16-byte entry stride), the entry pointer was `0x26035EE17F0` and its `+8` dword count was `0`; index 0 was null/count 0. The separate +0xA0-derived entry below had count `1`, so A3 took the +0xA0 path.

The caller at `sub_7FF6D1EFD340` checks the first returned entry's count (`[out+0]+8`), then the second (`[out+8]+8`); it uses a found entry only when its count is nonzero. If both counts are zero, it invokes ScriptInstance vtable `+0x30` and may return the global `dword_7FF6D4461288` fallback. In the historical capture, the +0xE0-derived count was zero and +0xA0-derived count was one. The found-entry path calls `sub_7FF6D2A462E0`; its return is serialized by A3 as kind `0x0A`, copying its first 32-bit word. The later guarded decode identifies that word as the GameMode network entity ID `0xD0000010`.

The nonce helper at `0x7FF6D12D7C60` uses the first seed XOR `0x316BFB92484F568C` and second seed XOR `(ROR64(qword(PEB+0x110),3) + 0x316BFB92484F568D)`. A read-only `NtQueryInformationProcess(ProcessBasicInformation)` call on the validated client returned PEB `0xEAA8C92000` and qword `PEB+0x110 = 0x7FFA876F65C8`. With those runtime values and the live key table at VA `0x7FF6D41046D0`, the table indices are **byte offsets**, not qword indices: `table+0x156` is `0x7CF6CAA4C508871E` and `table+0x2BF` is `0x90819AF38549392C`. F2A0A0 therefore produces component-114 slot `0x25F8C685FB8`; its entry pointer is `0x26035EE15D0` and `+8` count is `1`. This confirms the A3 lookup finds component 114 on its +0xA0 path.

The found entry's first qword is separately protected. For seed `B366E842871E4385` (first) and `D4AD0C1395FD6603` (second), the helper applies the same first-seed XOR and PEB-derived second mask. With `x` the encoded qword: stage 1 preserves `lo=x.lo`, and sets `hi=x.hi XOR (2*lo - ROL32(key(table+(first>>52)).lo,9))`; stage 2 preserves `lo`, and sets `hi=hi XOR (ROL32(key(table+(first&0xFFF)).hi,1)+lo)`, then XORs the second seed across 64 bits; stage 3 sets `hi=hi XOR (2*lo+0x533F8D5)`; final stage sets `hi=hi XOR (lo-key(table+(first>>52)).hi)` while preserving `lo`. The key table uses byte offsets. A3 passes this decoded pointer to `sub_7FF6D2A462E0`; do not treat the list pointer or raw component qword as an entity pointer. For the direct E8 callsite used here, D2A462E0 takes the path at `0x7FF6D2A46576`: load global qword `0x7FF6D41047FC`, ROL64 by 2, XOR `0xF320E42472A94F14`, XOR `[RCX+8]`, add `0xB0`, return. The preceding instruction overwrites RCX with the constant, so the decoded-component pointer itself is not XORed here. A3 serializes the returned address's first 32-bit word as kind `0x0A`.

A fresh guarded decode against graph 8420 metadata for PID `25896` returned network entity ID `0xD0000010`, matching the local GameMode entity. After the mode phase, the graph's state-8 branch byte was `1`; this confirms that the client condition selected its true branch in that capture.

## State 3 native begin callback

A second bounded read of the still-live PID captured state 3's runtime vtable `0x7FF6D386B870`; its `+0xB8` callback is `0x7FF6D1F797D0`. This is runtime-instance evidence, distinct from the schema getter/vtable in the graph metadata. The same callback address appeared for UX states 9, 10, and 14.

The callback at `0x7FF6D1F797D0` builds a small record with tag `4`, the schema state index read from `[descriptor+0x18]`, and the runtime state index read from `[state+0x70]`. It routes that record through `0x7FF6D2D92DE0` into the owner's context handler at `[context+0x98]` (`0x7FF6D2DC4A10`). The callback itself contains no direct branch on `m_hero`, dynamic variable `18405`, or the HUD visibility condition. Its generic downstream handler may process additional state; this trace does not identify the missing visual prerequisite.

The static downstream dispatch path at `0x7FF6D2DC4A10` wraps the record and calls `0x7FF6D2DC64F0`. That dispatcher first invokes the input object's vtable `+0x10` against a shared interface descriptor. If accepted, it uses the object's 16-bit key and the context table to resolve an entry; otherwise it evaluates the object through the statescript VM and uses the result to resolve an entry. The fallback returns false if the owner context is null, evaluation yields no result, or no object resolves. Either path needs a non-null resolved entry/object before reaching `0x7FF6D2DC7550`; that routine performs another compatibility check and updates state flags. It then calls `0x7FF6D2DC6E40`, which returns early when the callback-context byte `[qword([context+0x90]+8)+0x438]` is set and otherwise dispatches virtual callbacks (`+0xA8`, and for populated lists `+0xD0/+0xD8`). These are concrete generic dispatch gates, but static data does not show which branch node 3 takes or prove that this dispatcher creates the UX presenter.

The graph data gives one concrete type constraint: node 3 has `m_hero=null`, `m_entityID=3179`, and output dynamic variable `m_45017CEA=18405` with entity scope. Child node 4 references `18405` as an entity in its `m_45216F79` condition and separately reads entity variable `18406`. `18405` is therefore an entity-scoped output, not a boolean gate. The previous idea that seeding it as `Bool(true)` would fix the HUD was unsupported. Node 3's `m_87276FE6` expression uses entity `17937` and key `7423`; VM opcode 15 performs an external lookup using that key, so `7423` is not expected in the local owner variable bag.
