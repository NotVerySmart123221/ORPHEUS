# PLAY menu: Practice vs. AI card and the locked cards (2026-11-03)

Goal: hide the two locked PLAY cards (Tournament Match, Game Browser) and show the game's own Practice vs. AI card, which opens its EASY / MEDIUM / HARD choice. **Status: done with an ASI plugin (2026-11-03).** `tools/asi/retail_menu.asi` gives the retail main menu, and its TRAINING screen carries the native Practice vs. AI card and difficulty choice; the lobby answers the queue request (see "Retail menu via ASI" at the end). Without the plugin the Tournament Match card stays the vs-AI entry. Findings, then the routes.

## What picks the cards

- On the tournament route the PLAY screen shows three cards: Practice Range, Tournament Match (locked, "Tournament match not yet created.") and Game Browser (locked, "Unavailable while in a group") (`main-menu/tournament-play-cards.png`).
- The screen is UI graph `0x0B7C`. A read-only scan of the live client at the PLAY menu found it running (`tools/research/scriptlist.py`; 41 states). It references every PLAY card string: QUICK PLAY, Competitive Play, Arcade, GAME BROWSER, TOURNAMENT MATCH, PRACTICE RANGE. It also references the Training graph `0x0B7F`, which carries TUTORIAL, PRACTICE RANGE and PRACTICE VS. AI and embeds the Vs. AI queue card `0x0BE9` with the EASY / MEDIUM / HARD buttons (`practice-vs-ai-data.md`). `0x0B7F` is not instantiated in the tournament menu.
- `0x0B7C` state 10 is a BooleanSwitch (`tools/assets/graph_edges.py B7C`):
  - true branch: state 15, then presenters 13 and 8, the three tournament cards. This is the live branch.
  - false branch: Stacks 35 and 24, the retail layout. Idle.
- Its condition is `STU_2B33EE38`, a `STUConfigVarBoolBase` with no fields. In the client (IDA, dump image base `0x7FF6D1220000`):
  - its runtime class (constructor registry key RVA `0x2D76DA0`, vtable `0x7FF6D38840D8`) evaluates to the byte at `0x7FF6D404F448`;
  - the same byte doubles the lobby's player cap from 12 to 24 (`0x7FF6D1658800`, `0x7FF6D1658820`);
  - it is the `--tank_TournamentMode` flag.

  The server cannot change it, and process writes are out of bounds.

## Routes tried

- **ShowMode** (`--tank_ShowMode`, same direct dial, Pod 1 / Group 1). The game runs fullscreen at the desktop size, and only a desktop grab captures it (`PIL.ImageGrab`). Clicks use desktop pixels:
  - POD (1060, 1264), GROUP (1060, 1316), START (2560, 1332), needing a foreground click;
  - name (2560, 1120), ENTER GAME (2560, 1228), foreground.

  It logs in like tournament mode (0x5528, then our 0x5014/16/18/19), then sends two requests we never answer, and stays at "Entering Game":
  - group 41 (CRC `75D32AE2`, message ids `0x56B8`..`0x56CF`), offset 1, payload `1F`;
  - group 48 (CRC `888716D3`, ids `0xCEA4`..`0xCEB0`), offset 0, 40 bytes `00×8 FF×8 00×16 01 03 00 00 00 00 FF 00`.

  Their names and replies are unknown. ShowMode is a broadcast mode, so its menu is unlikely to carry Training anyway.
- **Retail route.** The lobby protocol notes (rentry `3bswrgmw`, "Tournament and retail routes") say the retail PLAY layout comes only with the retail route. That route takes its lobby address, keys and client id from a Battle.net referral. That needs a Battle.net stand-in, which this project does not have.

## Tournament Match card (2026-11-03)

- A data scan of every statescript graph (`.scratchpad/pva/menu_refs.py`, 42 min) for the tournament strings:
  - `0x0B7C` (the PLAY screen) uses only "Tournament match not yet created." (`0x0DE0000000005007`). It sits in a UXDisplayText (instance 164) that feeds UX data 163 and node 940 (`STU_C43F9944`: `m_gameMessage`, `m_params`, text). Node 940 hangs off the screen's root presenter, state 18 (instance 66, output var 6861). So the lock text is a toast the presenter fires on an event (the card's click), not a lobby string.
  - `0x1147` (client-only, 24 states) holds "Load/Reload Tournament", "Force set as tournament match", "Clear tournament match", "Clear Tournament". It also reads the match score vars 7901, 7854, 7855: an in-match tournament admin panel. Its actions run inside a custom game, not from the PLAY menu.
  - `0x0BCE` holds "Tournament ID: %1$s, Match ID: %2$s, Game Number: %3$s".
  - `tournament.createMatch %1$s %2$s` and "Custom game set as tournament match." are in no graph and not in code: probably server-side text.
- So the card unlocks only when the client already knows a tournament match exists. That state comes from the lobby, and its message is not known. The in-match "Force set as tournament match" needs a custom game first, which this server does not host.
- **The card is clickable despite the padlock.** A click sends lobby group `0x692C511B` (index 37 in this session), message offset 0, 26 bytes (`25 00 01 00 00 00 83 dd e9 6a 00 00 00 00 8e dd e9 6a 00 00 00 00 69 7b dd 00`; fields not decoded). Answering it with the same game handoff (20600) as the Practice Range request puts the client into the match (`main-menu/tournament-card-vs-ai.png`: Hanamura hero select, "Attack"). `practice.py` now does that: Tournament Match = the hosted vs-AI map, Practice Range = the Range.
- Still not done: hiding the padlock and "Tournament match not yet created.", the Game Browser card, and choosing the difficulty in game.

  - expression arrays: `m_configVars` and the `m_expression` offsets point into the asset's dynamic area at header word 7; each array is a u64 count and a u64 offset;
  - A (evaluator `0x7FF6D1B73570`) asks a player-state object (`[qword_7FF6D41786E0+320]` table) through a virtual call: 0 offline. B (`0x7FF6D1B658F0`) and C (`0x7FF6D1B3DFC0`) are queue checks (C: queue state 1); 0 at the menu;

- **Training screen** (`0x0B7F`): card presenters 69 (Tutorial, slot 0), 104 (Practice Range, slot 1), 146 (Practice vs. AI, slot 2; UX var 13684 is the slot).
