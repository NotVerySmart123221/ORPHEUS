# Practice Range HUD restoration

## Findings

Graph `0x20E4` is the Practice Range HUD child of controller graph `0x13C1`. Its sole owner state is state 25 (`STU_9D7BF987`); node 34 consumes entity-scoped dynamic variables `17906` and `18405` and declares remote sync IDs `0x0D800000000045F2` and `0x0D800000000047E5`. Both variables are `ENTITY` scope, so graph `0x20E4` correctly has zero per-instance presence bits. See the pinned [1.74 graph catalog](https://github.com/Boi-027/overwatch-1.74-lobby-server/blob/0fa61b950dfc9c915cb2353d2873d6d4689c2a5e/data/game_graphs_174.json.gz) and the local scope correction in [soldier76-weapon-graph.md](soldier76-weapon-graph.md#L22).

The local controller frame creates HUD instance 4 under controller instance 1, state 42, and activates controller state bit 36. It currently sends only entity variables `2438` and `31435` ([heroselect.py](../tools/lobby/vendor/ow174/game/heroselect.py#L70), [line 95](../tools/lobby/vendor/ow174/game/heroselect.py#L95)). The match already knows the player entity and possessed body: component 44 points all three possession slots at `player.body` ([match.py](../tools/lobby/vendor/ow174/game/match.py#L279)). The current HUD controller frame does not send `17906` or `18405`.

Graph `8420` also contains client-only initialization nodes. Its Entry at node 8 leads to a BooleanSwitch whose condition reads variable `23604`; the true branch reaches Stack node 5, which writes variable `3179` from `STU_B5A0CAF0`. Stack node 6 can then write variable `17937` from `3179` through `STU_0AC15F78`. Node 3 also references `18405` in its event path, and UXPresenter node 13 sends `17906` as a remote-sync payload. A full scan of the pinned graph catalog found no Stack or action node assigning `17906`, `18405`, or `23604`; graph 463 also carries `17906` as the payload of remote-sync ID `0x0D800000000045F2`, while graph 8420 state25 consumes `17906` and `18405`. These records establish use and flow, but do not name the hashed values or establish the meaning/polarity of condition `23604`. The graph catalog marks nodes 8 and 10 client-only. Local statescript notes say server-created instances skip their own Entry processing while client-only Entry nodes run ([statescript.py](../tools/lobby/vendor/ow174/game/statescript.py#L18)). So available evidence does not support “the client-only Entry never executes”; the gate may instead prevent its initialization branch, or the graph may lack required entity values.

## Minimal candidate and limits

The source identifies the missing HUD inputs but not their values: the exact assignment of player entity versus body entity to `17906` and `18405` is unresolved, and neither variable has a graph-side setter in the pinned catalog. Node 34 lists both without names. Do not treat either ordering as verified. `Graph(0x20E4, 1, 0)` remains the correct state/presence shape.

The earlier HUD-only runtime experiment activated the graph's sole owner bit and showed no HUD; it did not establish whether those two entity variables were present, and it did not test their assignments ([soldier76-weapon-graph.md](soldier76-weapon-graph.md#L20)). Therefore neither the owner state nor a candidate entity-variable binding is runtime-validated yet.

## Evidence boundary

- **Direct source evidence:** graph/node IDs, scopes, state and parent wiring, variable references, and current frame contents cited above.
- **Inference:** `3179` is a local/player entity input and `17937` is likely a possessed-body reference; the graph stores `3179` into `17937` through an entity conversion node, while the match's possession component independently identifies `player.body`.
- **Unknown:** names/roles and runtime values of `17906` and `18405`, the semantic condition represented by `23604`, whether client-only initialization currently takes its true branch, and whether supplying the two entity variables alone renders HUD elements.

## Native inspection of `STU_A3DEF368`

The retail image's STU metadata for class ID `0xA3DEF368` is at `0x7FF6D424A320` (class ID at `+0xB0`). Its type-key pointer at `+8` resolves to RVA `0x2D77AB0`; the local [state constructor registry](soldier-runtime/state-constructors.json#L3965) maps that key to constructor RVA `0xD0AF80`, vtable RVA `0x2662760`, and DSR RVA `0xCDDC20`. The constructor stub stores that vtable pointer. Static disassembly of vtable slot `+0x158` (`0x7FF6D1EFDC20`) is only `lea rax,[rip+0x203B269]; ret`, returning the global at `0x7FF6D3F38E90`. Adjacent slot `+0x160` walks that global's linked list and tests membership; slot `+0x168` compares against its head. A different slot, `+0x1B0` (`0x7FF6D1EFE380`), returns the qword at `[rdx+0x370]`. That is a context-field getter candidate, but static evidence inspected so far does not establish what object `rdx` points to, what `+0x370` means, or whether this value is a game-mode or player entity.

This does **not** resolve the HUD condition. The registry DSR is not evidence that `23604` equals either `player.entity` or `player.body`; the client-side config-variable evaluator/value path remains unidentified. The hypothesis that `0xA3DEF368` resolves to the game-mode entity is still unverified. Do not change the entity-variable assignments based on this native callback table alone.

At retail build 104319, STU metadata maps `STU_B5A0CAF0` to type-key RVA `0x2D76040` and `STU_0AC15F78` to `0x2D76930`; the [constructor registry rows](soldier-runtime/state-constructors.json#L9105), [and](soldier-runtime/state-constructors.json#L8895) map them to vtable/DSR RVAs `0x26641B8`/`0xCEFFA0` and `0x2663D90`/`0xCEDD80`, respectively. Their vtable slots are native virtual methods, but the static table alone does not prove which graph expression calls them or what semantic identity their outputs have.

## Native comparison of config-var slot `+0x1B0`

The three config-var vtables differ at slot `+0x1B0`. `STU_A3DEF368` (vtable RVA `0x2662760`) points to VA `0x7FF6D1EFE380` / RVA `0xCDE380`; the method is `mov rax, [rdx+0x370]; ret` and ignores `rcx`. `STU_B5A0CAF0` and `STU_0AC15F78` point to the same VA `0x7FF6D1B5CA10` / RVA `0x93CA10`. That method calls `this->vtable[+0x20]`, then returns its fifth argument if the callback is true, otherwise null. These methods have different contracts despite sharing the same slot number.

Static xref queries find no direct code xrefs to the `A3DEF368` getter or its vtable slot; its use is through virtual dispatch. Other `+0x1B0` call sites show incompatible argument patterns: e.g. `sub_7FF6D16547E0` passes a byte-stream pointer in `rdx`, while `sub_7FF6D2D926C0` passes a runtime graph-state pointer. The offset is interface-specific. Neither the accessor's `[rdx+0x370]` load nor the condition graph proves that `rdx` is the expression context, or that `+0x370` is a game-mode entity. That field's type/meaning remains unresolved.

## Native config-value callbacks at vtable `+0xC8`

The actual class vtables confirm these `+0xC8` methods: `STU_A3DEF368` (`0x7FF6D3882760`) -> `0x7FF6D1EFD810`, `STU_B5A0CAF0` (`0x7FF6D38841B8`) -> `0x7FF6D1F10550`, and `STU_0AC15F78` (`0x7FF6D3883D90`) -> `0x7FF6D1F0E410`. Each reads its context through the `rdx` object’s `+0x30` virtual and writes a typed result through the caller-provided output wrapper. The `A3DEF368` path uses `sub_7FF6D2187090`, which sets wrapper kind `4` and stores a 64-bit scalar. The B5/AC paths use `sub_7FF6D2187550`, which sets kind `6` and copies three 32-bit words (12 bytes); their caller routines perform floating-point transform operations on the associated values. These wrapper kinds establish result shape, not semantic identity.

Graph `8420` state/node 10 uses `A3DEF368` with dynamic variable `23604`; node 14 also includes `A3DEF368`. Its returned scalar remains opaque, so the call path does not prove that `23604` is a mode, player, or body entity. Graph `8420` node 5 uses `B5A0CAF0` without custom fields. Node 6 uses `0AC15F78` with `m_entity = DynamicVar(3179)`. Both vector callbacks resolve a config field, query the context, then pass through large entity/transform routines before producing the 12-byte result. This supports a context-derived vector result; it does not establish whether it is position, another transform value, or which entity it describes. No assignment changes follow from these callbacks alone.

Parent's fresh diagnostic outcomes: after resetting the HUD, `hud-gate-bool` and `hud-mode` each restore only the red blocked icon; neither renders the HUD. This is consistent with these single-variable candidates being insufficient, but does not identify the missing input.

The pinned [build 104319 graph catalog](https://github.com/Boi-027/overwatch-1.74-lobby-server/blob/0fa61b950dfc9c915cb2353d2873d6d4689c2a5e/data/game_graphs_174.json.gz) shows graph `8420` node 13's Stack `m_value` is `STU_B5A0CAF0`; node 14's Stack `m_value` is `STU_0AC15F78`, whose serialized `m_entity` wraps `STUConfigVarDynamic` identifier `3179`. The same graph uses `STU_B5A0CAF0` as a BooleanSwitch config var. This establishes serialized graph relationships only. The catalog provides no semantic name for either hash or for dynamic variable `3179`.

Graph `8420` has three client-only `UXPresenter` nodes (states 9, 10, 14) with opaque presenter IDs `0x0A880000000002BE`, `0x0A88000000000236`, and `0x0A88000000000251`. Soldier: 76's body entry lists weapon graph `596`; that graph has three additional `UXPresenter` nodes (states 68–70) with IDs `0x0A8800000000023F`, `0x0A88000000000240`, and `0x0A880000000002AB`. The catalog labels none as crosshair or ammo, so those IDs are candidates for presenter assets, not confirmed HUD widgets.

Graph `8420` appears in the root-graph list but in none of the catalog's 32 hero-body graph lists. The local implementation treats `0x20E4` as the Practice controller's HUD: [statescript.py](../tools/lobby/vendor/ow174/game/statescript.py#L37) pairs it with Practice controller graph `0x13C1`; [heroselect.py](../tools/lobby/vendor/ow174/game/heroselect.py#L62) creates its instance only when that controller has `hud_bit`. The current `controller_frame(PVP, select_open=False)` does **not** probe child `0x0215`: `PVP` has `hud_bit=None`, so the helper only activates state 119 and creates the hero-select instances. `select_open=False` sets variables 2438/31435 false; it does not remove the hero-select subgraph ([controller definitions and frame assembly](../tools/lobby/vendor/ow174/game/heroselect.py#L53-L96)). ## Runtime state factory path

Static IDA analysis distinguishes the compiled graph node from the allocated runtime-state object. The state lookup at VA `0x7FF6D2DB3000` (RVA `0x1B93000`) reads the compiled-node flag at `+0x78`: true routes to allocator/registration path RVA `0x1B91460`; false routes to the stateless cache path RVA `0x1B92DA0`. The false path indexes its cache by compiled-node `+0x6C`, then asks the node's vtable slot `+0x8` for a registry key. If that lookup misses, it queries the node through vtable slot `+0x10` using interface descriptor VA `0x7FF6D3FF5430` (RVA `0x2DD5430`); if supported, it looks up that generic interface in factory registry VA `0x7FF6D44B69E0` (RVA `0x32969E0`).

This explains why absence of class key `0x2DF2F58` from the captured concrete factory-key list does not prove that state 25 has no runtime object: the stateless path can use the generic interface factory. It does **not** establish whether graph `0x20E4` state 25 has compiled-node `+0x78` set, whether the generic interface test succeeds for that node, or what runtime vtable is returned. The `STU_9D7BF987` metadata object's vtable remains schema serialization metadata and cannot stand in for the live state's vtable. I did not run the broad live-process heap reader because the currently available cached result is from a prior PID and cannot identify the current HUD instance; no live heap data was used for this finding.

## Generic stateless factory result

A fresh bounded `state_types.inspect` read of the current hash-verified client found the generic interface descriptor key used by the false branch: registry `key_rva=0x2DD5430`. Its factory row points to prototype vtable RVA `0x261BD78`; this is the generic factory prototype returned by `sub_7FF6D2DB04C0` on a matching interface key, not the `STU_9D7BF987` schema vtable. The local [reader](../tools/research/state_types.py#L36) derives prototype vtable and DSR RVAs from the registry value at lines 59–69. The registered value's `+8` callback is RVA `0x1B72650` (bytes `32 C0 C3`, returns false); do not treat this callback as a conventional allocating constructor.

For that prototype vtable, `+0x158` points to RVA `0x1CE5640`, a shared `ret 0` implementation (DSR no-op). Slot `+0x50` points to RVA `0x1B6EE40`, which calls `0xF5B6C0` and returns its boolean; this is the callback invoked by the stateful create path after object creation, but the false stateless fallback itself only caches the prototype. Slot `+0x58` points to RVA `0x1B6EE60`, which calls RVA `0xF606C0` and returns its boolean. Slot `+0xB8` points to RVA `0x123CC10` (`xor al,al; ret`); `+0xC0` points to RVA `0x1B73D80`, which dispatches through the queried object's `+0x138`, `+0x198`, and `+0x130` methods and may set a flag at its `+0x40`. The vtable and callbacks identify the generic fallback implementation, but do not prove that HUD graph state 25 takes that fallback or that it is the missing HUD state; node `+0x78` and the interface check for the live HUD node remain unobserved.

The verified runtime vtable's DSR slot `+0x158` and remote-sync descriptor slot `+0x168` both point to VA `0x7FF6D2F05640` (RVA `0x1CE5640`, `ret 0`). This class consumes no owner-frame DSR bits and contributes no remote-sync descriptors. The Begin classifier at VA `0x7FF6D217E960` / RVA `0xF5E960` reads class ID `0x7A7F2732` and returns false, so no separate Begin-control bit is required. That does **not** mean Begin has no side effects: runtime vtable slot `+0xB8` points to VA `0x7FF6D1F797D0` (RVA `0xD597D0`). This proves Begin needs a valid context/table entry to create a presenter; it does not identify the correct row, prove the interface query outcome, or explain why the current client renders no HUD. This resolves wire shape, not which UX asset renders health, ammo, crosshair, or the main HUD.

## Graph 596 parent and branch states 9, 40, and 67

Catalog state 9 (RID 22, owner bit 9) is generic `STUStatescriptState`; its subgraph lists states 67, 40, and 69. Its schema metadata class ID is `0x7C37840C`, key RVA `0x2DD53F0`. The Begin classifier at RVA `0xF5E960` has no class-ID case for `0x7C37840C`, so it follows the false path; state 9 needs no extra Begin bit.

States 40 and 67 are `STUStatescriptStateBooleanSwitch` (class ID `0x76F0CF47`, key RVA `0x2DF2DF8`). Their runtime vtable VA `0x7FF6D39D03B0` has DSR slot `+0x158` at VA `0x7FF6D2DB92D0` (RVA `0x1B992D0`) and descriptor collector slot `+0x168` at VA `0x7FF6D1F64BF0` (RVA `0xD44BF0`). The catalog nodes declare no node-level remote-sync IDs (`m_BF5B22B7` and `m_8BF03679` are null), so do not infer additional graph-authored remote values from that internal descriptor callback.

State 67 tests instance variable `10268`; true selects child state 68 (owner bit 64), false selects state 70 (owner bit 66). To target the requested diagnostic pair, owner bits 9, 63, 65, and 66 correspond to states 9, 67, 69, and 70; branch values must be state 67=false and state 40=false if state 40 is explicitly activated. This is a catalog/runtime-wire mapping, not proof that the pair renders the desired HUD.
