The extracted hero catalog marks `0x16B.075` as `Training Bot`; it does not itself supply the gameplay-entity join. ## Diagnostic attack decision

`TrainingTarget.attack_player(position, now)` now makes a deterministic target-side decision: target must be alive and present; player must be within 20 m and inside a 25-degree forward cone; first attack waits one second, then decisions return 20 damage at one-second intervals. Death/respawn resets its attack clock. The method only returns damage; it does not apply player health or run from production match flow. Map occlusion, vertical aim, projectile travel, target tracking, and native bot AI are not modeled. This is a controlled diagnostic shortcut, not an original bot behavior claim.

The match integration needs a player health value initialized at 200, updated through component 51 (`world.health(current, 200)`) when the decision returns damage, and an explicit diagnostic-phase gate around the call. `Player` currently has no mutable health/dead/respawn fields. At zero HP, schedule one respawn and use the existing body replacement path: `Player.new_body()` assigns a fresh body ID and resets movement to spawn; `Match.switch_hero(player, player.hero)` additionally recreates component 51 at full health, updates player possession components 44/75, and destroys the prior body. The integration must prevent repeated death handling while waiting and reset health on replacement. Source: [`world.health`](../tools/lobby/vendor/ow174/game/world.py#L146), [`Match._body_create`](../tools/lobby/vendor/ow174/game/match.py#L300), [`Player.new_body`](../tools/lobby/vendor/ow174/game/match.py#L155), and [`Match.switch_hero`](../tools/lobby/vendor/ow174/game/match.py#L535).

Focused tests cover initial delay/cadence, dead or removed target suppression, range and facing, cadence reset on fresh target identity, and existing target damage/respawn behavior: `python -B -m unittest test_target` from `tools/lobby` (10 tests pass).
