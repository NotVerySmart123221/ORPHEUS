# Rust becomes the default branch

The cutover is scheduled for **Thursday, November 19, 2026 at 12:00 UTC (14:00 Helsinki)**. Until the cutover, Python contributions target `main` and Rust contributions target `rust`. Afterward, the Rust server is the only maintained implementation. Python remains available as a read-only reference on `python-archive` and accepts no new pull requests. All further development targets the Rust `main`.

This is a change in maintenance policy. The Rust server is still a developer preview. Soldier and Practice Range behavior, combat feedback, and original-client stability continue to need verification. Keep test results associated with their implementation, commit and runtime manifest.

## Maintainer cutover checklist

1. Before the window, list open PRs by **both** base and head. Record the exact Python `main` and Rust `rust` SHAs, the current default branch, branch protections/rulesets, required check names, and any active merge queues. Finish reviewed work before the freeze. Coordinate a disposition with the authors of pending Python PRs, including drafts. Preserve their discussion and commits. Open a separate Rust PR for work appropriate to the native implementation. A change of base across these implementations is rarely a clean port.
2. At the window, stop merges and record the final SHAs again. Use GitHub's **Rename branch** operation to rename Python `main` to `python-archive`, then Rust `rust` to `main`. Record the UTC second the archive name first exists. This is the guard cutoff, including PRs submitted during the handoff. Set the new Rust `main` as the default. Verify `git ls-remote --symref origin HEAD refs/heads/main refs/heads/python-archive` reports the new default and both recorded tips. Existing tags should still resolve to their original objects. If either rename fails, stop the cutover and inspect the surviving refs before proceeding. [GitHub branch rename behavior](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/renaming-a-branch).
3. Before cutover the active `Protect main` and `Protect rust` rulesets target exact refs (`refs/heads/main` and `refs/heads/rust`). Both require PRs and checks and block force pushes; neither contains a deletion rule. Inspect the effective rules after each rename. Retarget the Rust ruleset to the new `main`, remove any obsolete Python check requirements from that ref, and verify required Rust checks and up-to-date PRs. Configure the desired deletion protection explicitly. Confirm an ordinary Rust PR triggers the required checks on the new base. On `python-archive`, apply an exact-name read-only lock (including admins), disable fork syncing and block deletion/force pushes. Confirm the effective rules for each branch, including repository and organization rulesets. [GitHub branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
4. Audit open PRs again. GitHub updates PR bases on rename and can close an open PR that uses the renamed branch as its head. Reconcile these against the inventory before enabling the archive policy below. Review workflow branch filters, explicit checkout refs, shared-contract inputs, default-branch schedules, private runner trusted refs, docs and branch links. Point Python reference inputs to the archived SHA or `python-archive`; point Rust CI to `main`. Keep the existing Git history and release tags intact.
5. After both tips, default, locks and PR dispositions are verified, set the Actions repository variable `PYTHON_ARCHIVE_GUARD_SINCE` to the **archive creation timestamp recorded in step 2**, formatted as `YYYY-MM-DDTHH:MM:SSZ`. The archive guard workflow must be present on the new default branch. Run it manually once and check its result. Record final SHAs, time, protections and links to outstanding work in the cutover announcement.

The lock prevents new commits and merges. GitHub still lets users open PRs against a locked branch. The archive guard runs on the trusted default branch every 15 minutes and can be dispatched manually. Its first run includes the rename window. It closes PRs opened, reopened or retargeted to the archive since the recorded cutoff. An older PR with no such later event stays on the maintainer's inventory. The live base check and close are separate API requests. If a contributor retargeted a PR at that instant, verify its base before reopening it. Scheduled jobs can be delayed or disabled by GitHub. If the job is unavailable, the lock remains in effect and a maintainer should review archive-targeting PRs. No private runner or game data is involved.

## Existing local clones

After the switch, run `git fetch origin --prune` and `git remote set-head origin -a`. Check `git branch -vv` before pulling or pushing. For a local Python checkout named `main`, preserve local work by renaming that local branch to an unused name, then set its upstream to `origin/python-archive`. Create or retarget a local Rust branch to track `origin/main`. A fresh clone after the switch checks out Rust by default.
