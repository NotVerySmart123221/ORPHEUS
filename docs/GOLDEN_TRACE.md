# Golden gameplay traces

**Design proposal, build 104319.** A private golden trace would answer one question: given the same inputs and virtual clock, at which tick did the native server first produce a different gameplay outcome from the pinned Python reference? A matching result would cover the fields and inputs in a named comparison profile. Original-client acceptance is tracked separately. [Implementation issue #131](https://github.com/leafall903/ORPHEUS/issues/131)

## First comparison profile

Start with one room, one Soldier and one identified Practice Range bot. Align one fresh body lifecycle, accepted movement/aim/button input, rifle fire and reload, the bot’s health/death state, and creation of its next body. Capture the state after the room tick and the ordered gameplay outputs for that tick. Extend coverage to Sprint, Helix and Biotic Field under a new profile revision once the corresponding Python behavior has current original-client evidence.

1. **Inputs.** Keep offered input and actual acceptance distinct. For each tick, store virtual elapsed time (integer microseconds), missed-tick count and an ordered list of command submissions with room, player, body epoch, frame, forward/right, yaw/pitch, buttons, action, extra and optional click/subframe/aim. Specify the exact mapping of Python's click fields and Rust's optional click using a synthetic contract before recording. The first profile uses gap-free submissions and deterministic tick advancement. Duplicates, retries and loss require an explicitly defined delivery schedule and a new scope. Recompute acceptance, hits, damage and outputs in each server.
2. **Identity.** Use named scenario participants and monotonic body generations, such as `player/0/body/1` or `bot/0/body/2`. Map VM instances by body generation, parent path, graph identity and occurrence within that parent's observed creation order. Preserve child slot or creation site when it has gameplay meaning. Keep raw allocator IDs as optional local diagnostics. A missing lifecycle boundary or ambiguous sibling mapping makes the comparison incomplete.
3. **State.** Require explicit lifecycle, alive/health, rifle ammo, reload state and accepted command frame for this profile. Expose position/aim using the numeric rule below. Emit separate rows for semantic VM parent/child identity where required. Gather data from stored state after advancing once. Calling an accessor that drains pending events, evaluates a graph, allocates a slot, draws RNG or performs a second tick would change the run.
4. **Outputs.** Observe the records actually emitted through the existing send path, using a sink in the controlled harness. Emit ordered tuples of recipient role, message/record kind, lifecycle identity and the profile’s defined semantic fields. Maintain datagram boundaries in the output sequence where grouping affects delivery. Record duplicate and absent outputs; represent an empty tick explicitly. Optional byte lengths and packet counts are local diagnostics. Any record relevant to the selected profile that cannot be decoded is an incomplete result. Raw datagrams are outside the format.

Both implementations need an adapter. Use the existing Python reference self-replay and Rust headless tests to verify that attaching an observer leaves input decisions, state transitions and emitted records unchanged. In a frozen Python archive, keep the recorder in a separate reviewed tool against the pinned reference; record the adapter revision as provenance.

## Private format and first-difference report

Use newline-delimited JSON with a versioned header, contiguous tick rows, then a required end row. This is a proposed interface for R1.3.

- **Header:** schema/profile revision and required fields, build, scenario and initial lifecycle, exact runtime manifest SHA-256, reference and adapter commits, domain-specific seed/clock configuration, input schedule fingerprint and platform fingerprint. Record OS/architecture, interpreter/compiler versions, floating-point build settings and relevant dependencies. Candidate Rust revision is comparison metadata; pin it for a rerun. The reader verifies the reference selection and both inputs before comparing.
- **Tick:** tick index, virtual clock/missed ticks, ordered inputs for this tick, canonical state rows, ordered effects and their digest. Each state row is `[lifecycle, field, value]`; sort rows by the pair of ASCII keys and reject duplicates. Sort only semantically unordered collections. Preserve FIFO, delivery and activation order. Include enough field values locally to report an actual diff even when a hash fails.
- **End:** expected last tick, number of tick rows and SHA-256 of all preceding canonical header/tick lines with LF terminators. Reject truncated or extra rows, unknown required fields, mismatched hashes, missing inputs and incompatible profile/build/manifest/platform. Distinguish `incomplete` from a complete `mismatch` or `match`.
- **Numbers and hashing:** use booleans, bounded integers, validated ASCII field/enum names, arrays and objects. Use explicit null only for an allowed absent value; absence of a required field is incomplete. Give large IDs a fixed-width lowercase hexadecimal string representation. Canonical JSON uses sorted ASCII object keys, decimal integers, compact separators and UTF-8. SHA-256 for a tick projection covers precisely the bytes of the object with keys `effects` and `state`, without a trailing newline.
- **Floating point:** prefer already-defined quantized game units where both implementations expose the same rounding and units. For unquantized required state, encode finite IEEE-754 bits at the declared field precision as fixed-width big-endian lowercase hex. Explicitly define whether signed zero is meaningful for each such field; preserve both by default. Reject nonfinite values. Record and replay on the same platform/architecture. Same hardware limits drift, but library functions, rounding and fused operations can still disagree. Keep the first exact difference; use local numerical deltas for diagnosis. Any change in precision or comparison policy requires a reviewed new profile and newly recorded reference.
- **Diagnosis:** compare input acceptance first at the ordered boundary, then state fields, then ordered delivery groups/effects. Return the first differing tick, phase, logical entity and field/index with local expected/actual values. Also detect a missing entity/effect and ordering differences. A hash alone cannot identify the field.

A wholly invented one-tick projection, showing the encoding only:

```json
{"effects":[],"state":[["player/0/body/1","alive",true],["player/0/body/1","ammo",3]]}
```

SHA-256 without a line terminator: `43509cdb3d72c38a4625c41276426c777d728ad1771dcac4c9692e49aefa5051`. Changing the candidate's ammo to 2 should identify `player/0/body/1`, field `ammo`, at that tick. This example has no original-client evidence.

## Recording and promotion

Only invented inputs and expected values belong in public fixtures. Store prepared traces, detailed per-entity observations and diffs under owner-controlled local storage (the private runner's golden directory or a maintainer's machine). Do not include profiles, keys, addresses, raw packets, memory dumps, or the Python journal's private stored-state graph. Keep private paths and game-derived values out of public logs and artifacts. A public check may report scope, revision, count, result and an approved manifest fingerprint.

Before using a Soldier trace as a migration gate, require two identical independent Python recordings on the same platform and two identical Rust runs from the same inputs. Test that the comparator catches a changed field, an extra effect, swapped ordering, a reused identity, a missing final tick and a different manifest/platform. Preserve the selected reference and a tagged client verification report. A first differing tick provides a debugging lead for [#72](https://github.com/leafall903/ORPHEUS/issues/72) or [#121](https://github.com/leafall903/ORPHEUS/issues/121) only if their relevant behavior is inside the declared scope. A stable trace or a single clean client session cannot close either issue.
